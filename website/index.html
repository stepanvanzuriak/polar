polar

A statically typed language that compiles to JavaScript.

Records, effects and hosts are checked before anything runs. What you ship is plain JavaScript with source maps and type declarations.

Records that fit any shape

title_of asks for a title and nothing more. A Task works, an inline record works, and a record without a title is a compile error.

types
  Task = { id: Int, title: String }

functions
  // `| rest` lets any other fields through
  title_of(r: { title: String | rest }) -> String {
    r.title
  }

  main() {
    let task: Task = { id: 1, title: "Write docs" }

    Log.info(title_of(task))
    Log.info(title_of({ title: "Ship it", author: "Ann" }))
  }
$ polar run records.px
Write docs
Ship it

Effects are in the signature

/ {Clock} says stamp reads the clock. double claims to be pure, so the compiler rejects the hidden call and says how to fix it.

effects
  Clock in Node {
    now() -> Int
  }

functions
  stamp(label: String) -> String / {Clock} {
    "#{label} at #{Clock.now()}"
  }

  double(n: Int) -> Int {
    n * Clock.now()
  }
$ polar check clock.px
error[POLAR0808]: `double` uses `Clock`, but its signature says it is pure
  --> clock.px:17:9
   |
17 |     n * Clock.now()
   |         ^^^^^^^^^^^ this uses `Clock`
   |
   = note: a signature with `->` and no `/ {…}` promises no effects
   = help: add `/ {Clock}` after the return type

Browser and server in one program

Visits lives in Node and Dom in the browser. The bridge line lets browser code call Visits over HTTP, and the build writes one bundle per host.

hosts
  Browser
  Node

effects
  Visits in Node {
    count() -> Int
  }

binds
  Visits in Node {
    count() {
      42
    }
  }

  Visits in Browser from Node

functions
  start() -> {} / {Dom, Visits} {
    Dom.append_text("p", "#{Visits.count()} visits so far")
  }
$ polar build
built visits (1 file) for Browser into dist/Browser in 118ms
built visits (1 file) for Node into dist/Node in 191ms

Zones that extend the language

routes isn't built into Polar. The simple_framework package adds it with a Rust plugin. :id fills the handler's id parameter, and the generated router is type-checked like your own code.

routes
  GET     /posts      -> index
  GET     /posts/:id  -> show

functions
  index() -> Response / {Posts} {
    Response.json(200, Posts.all())
  }

  show(id: Int) -> Response / {Posts} {
    match Posts.find(Id(id)) {
      Some(post) -> Response.json(200, post),
      None -> Response.not_found(),
    }
  }

Readable JavaScript out

Each module becomes an ES module with a source map and a .d.ts file, so TypeScript code can import it with full types.

types
  User = { name: String, admin: Bool }

functions
  greet(user: User) -> String {
    if user.admin { "Admin #{user.name}" } else { user.name }
  }
$ polar build greet.px --out dist
built 1 file in 5ms
$ cat dist/greet.js
import * as $rt from "./_polar/runtime.js";

export function greet(user) {
  if (user.admin) {
    return `Admin ${user.name}`;
  } else {
    return user.name;
  }
}
//# sourceMappingURL=greet.js.map
$ cat dist/greet.d.ts
export type User = { name: string; admin: boolean };

export declare function greet(user: User): string;

Functions ask only for the fields they use

Records are row-polymorphic. title_of accepts any record with a title, whether it's a Task, a Post or one written inline, and every field access is still checked.

types
  Task = { id: Int, title: String, done: Bool } derive(Eq, Json)

functions
  title_of(r: { title: String | rest }) -> String {
    r.title
  }

  complete(t: Task) -> Task {
    { ..t, done: true }
  }

Side effects are part of the type

/ {Posts} says this handler reads and writes posts, and nothing else. Functions without effects stay pure, and List.map passes its callback's effects through, so nothing slips past the checker.

effects
  Db in Node {
    find(id: Int) -> Option<Post>
    count() -> Int
  }

functions
  show(id: Int) -> Response / {Posts} {
    match Posts.find(Id(id)) {
      Some(post) -> Response.json(200, post),
      None -> Response.not_found(),
    }
  }

One program for the browser and the server

Declare the hosts your code runs on. polar build writes one bundle per host, each with only that host's bindings. A bridge lets the browser call an effect that lives in Node, with the same types on both ends.

hosts
  Browser
  Node

schema
  posts in Node
    id         Id<Post>  primary
    title      String
    author_id  Id<User>  references users

binds
  Posts in Browser from Node

Packages can add to the language

A package can define new zones with a Rust plugin. The example web framework adds schema, routes and views, and the code they generate goes through the same type checker as yours.

routes
  GET     /posts      -> index
  GET     /posts/:id  -> show
  POST    /posts      -> create

views
  card(post: Post)
    <article class="post">
      <h2>{post.title}</h2>
      <p>Post #{post.id}</p>
    </article>

JavaScript you can read

The output is ES modules with source maps and .d.ts files, so Polar fits into an existing Node or browser project. The build folder runs on its own with node dist/start.mjs.

$ polar build src --out dist
$ ls dist
main.js  main.js.map  main.d.ts  start.mjs

$ polar check src --watch
$ polar fmt src --check

Build from source

Polar needs Rust 1.85 or newer and Node.js. The docs cover the language, projects, packages and the standard library.

$ git clone https://github.com/stepanvanzuriak/polar
$ cd polar
$ cargo install --path cli
$ polar run hello.px
module Main

functions

    Log.info("Hello from Polar")
